## 2026-11-13: An HDMI screen's brightness follows the sun

<!-- prawduct: type=feature | scope=hdmi-brightness | closes=brookstalley/arrt-player#34 | release=v0.7.0 -->

An HDMI screen that answers DDC/CI now has its brightness set from the sun, as the Frame's has been, between a night level and a day level (`build-plan-hdmi-brightness.md`, chunks 01–03).

### What changed
- **Chunk 01, `ddc.py`:** a monitor's DDC/CI features over its HDMI connector's I2C bus, written directly from Python with no `ddcutil` (owner, 2026-11-13). The tests hold it to the bytes the reference LG exchanged on the Pi. The bus is found from the connector's sysfs `ddc` link. An unsupported feature, nothing answering, a garbled reply and a fault of this host are kept apart.
- **Chunk 02, `displays/screen_brightness.py`:** `ScreenBrightness` follows `brightness.level_at` between `SCREEN_MIN_BRIGHTNESS` and `SCREEN_MAX_BRIGHTNESS` (defaults 5 and 50), on `BRIGHTNESS_INTERVAL_SECONDS`.
  - It writes only when the value changes, so a brightness set by hand stays until the sun moves the value or the Player restarts.
  - It writes nothing to a screen that is dark or absent, and re-probes a screen that comes back.
  - It reads every write back.
  - It reports an unsupported or unanswering screen once, and never stops the wall.
- **`config.py`:** the screens' brightness is off with no location, or with `SCREEN_BRIGHTNESS=off`. The Frame and the screens read the location through one parser.
- **`brightness.py`:** a day with no dawn, dusk, sunrise or sunset (north of about 54.6° near the June solstice, and inside the polar circles) no longer raises from astral. That raise crashed any wall that followed the sun, the Frame's included.
- **Chunk 03, the Pi:** `display.service` adds group `i2c`, and `deploy/modules-load.d/arrt-player.conf` loads `i2c-dev` at boot. The Pi acceptance was observed with the owner at the monitor (`hdmi-output-findings.md`).

**Consumer note:**

Install `deploy/modules-load.d/arrt-player.conf` and the updated `deploy/display.service` as `deploy/README.md` § An HDMI screen's brightness follows the sun says. With `LATITUDE`, `LONGITUDE` and `LOCATION_NAME` set, every HDMI screen that answers DDC/CI then follows the sun between 5 and 50. Set `SCREEN_MIN/MAX_BRIGHTNESS` for other levels, or `SCREEN_BRIGHTNESS=off` to leave the screens alone. On a client with a Frame north of about 54.6°, the wall no longer crashes around the June solstice.

## 2026-11-13: The television's token file is private, and a cached ETag never outlives its document

<!-- prawduct: type=fix | scope=token-mode-and-stale-etag | closes=brookstalley/arrt-player#3,brookstalley/arrt-player#4 | release=v0.7.0 -->

Two defects that discovery filed, fixed on one branch.

### What changed
- **#3:** the television library wrote the pairing token with the process umask, so it was world-readable on the Pi and anyone on the Pi could use it to drive the set's art channel. `deploy/display.service` now sets `UMask=0077`, so everything the Player writes belongs to `tvpi` alone. `SamsungTv.connect` sets the token file to 0600 after every connection attempt, in a `finally`. A mode it cannot set is logged as `tv.token_file_open`. The Player never creates the file itself.
- **#4:** `Pull._adopt_feed` left the previous feed's `manifest.etag` behind after adopting a feed served with no ETag. When the server returned to the old feed, it answered that ETag with 304, and the wall stayed on a feed the server no longer served. The old ETag is now removed before the new manifest is written, and the new one is written after. A crash between the two writes therefore costs one full download instead of a stale ETag. `ClientPull` gets the same order.
- A test that passed with the token file's `FileNotFoundError` branch removed now asserts that no `tv.token_file_open` record appears.
- `project-preferences.md`: the norm that everything the Player writes belongs to its account alone, ratified by the owner 2026-11-11 and held by the unit's UMask test and `TestTheTokenFileIsPrivate`.
- Records: `security-model.md`, `observability-strategy.md`, `data-model.md` and `deploy/README.md` § The television's token is private to `tvpi`.

**Consumer note:**

On the Pi, install the updated `deploy/display.service` as the runbook says, then run `systemctl daemon-reload`. After the Player's next connection to the set, the token file reads mode 600, and nothing is re-paired.

## 2026-11-11: Slideshow mode, which plays a Reddit listing on an HDMI screen through mpv with no Arrt server

<!-- prawduct: type=feature | scope=slideshow | release=v0.8.0 -->

A Player can now run without an Arrt server. In slideshow mode it plays one
Reddit listing, in order and looped, on one HDMI screen at 4K. It shows stills,
GIFs and clips, muted, and captions each post on the e-paper label with its
title, subreddit, author and upvotes. The mode, the listing and the session
cookie are set on the settings page. The Player runs in one mode or the other,
never both (backlog #27).

### What changed
- **`PLAYER_MODE`** (`arrt`, the default, or `slideshow`), with `SLIDESHOW_URL`,
  `REDDIT_SESSION`, `SLIDESHOW_OUTPUT` (default `hdmi-a-1`) and
  `SLIDESHOW_MIN_SECONDS` / `SLIDESHOW_MAX_SECONDS`. A still shows for the
  minimum. A clip repeats until it reaches the minimum, and the total is cut at
  the maximum.
- **mpv draws the slideshow**, as a process the Player owns. It runs in its own
  process group and is stopped on every way out. One left behind by a Player
  that was killed is stopped at the next start. It is given files from the cache,
  never addresses.
- **A second HTTP client** (`sources/fetch.py`), which the plane-isolation guard
  bounds by what it can reach. API calls go only to `www.reddit.com` and
  `api.redgifs.com`, and the cookie goes only to Reddit. Media comes from any
  host a post links, but only at a public address, checked when the connection
  is made. A download is kept only if its bytes are a picture or a clip.
- **Media from any linked host.** Reddit's own copy of a post's media is used,
  and per-host resolvers fetch better copies where one exists: redgifs HD and
  imgur. A resolver that fails leaves the post with Reddit's copy.
- **A 2 GB media cache** under `$CACHE_DIR/.slideshow/`. It keeps what the
  current listing names and deletes the rest. The last listing is saved, so a
  restart while Reddit is down still plays.
- **Reddit answering anything but a listing never blanks the screen.** The
  cache plays on, and the page says why: listing refused, cookie rejected, rate
  limited or unreachable. The page also shows when the cookie expires.
- **The settings file is now layout version 2**, which adds the slideshow's keys.
- **Every log line is findable by its event field**, and a test walks every
  log call to keep it so. Tests that
  check something is absent from the log now read the formatted journal line,
  fields included, through `conftest.journal`, so a secret in a field cannot
  slip past them.
- **The slideshow's screen follows the sun**, as an Arrt-mode screen does
  (`SCREEN_*` and the location keys). It is written only while an item is up,
  and its journal lines carry `wall_id` `slideshow`.
- **Deploy:** the unit gains group `render`. `deploy/README.md` § The slideshow
  covers installing mpv, switching modes and rolling back.

### Confirmed by the owner (2026-11-10)
- The mode covers the whole Player; HDMI only for now.
- No NSFW filter: what the URL points at is the owner's choice.
- imgur albums show their cover image.
- 1080p clips upscaled by the display hardware on the 4K screen ("looks much
  better than before").
- mpv installed by the install and upgrade flow.

**Consumer note:**

**Install mpv before deploying this revision.** The runbook checks for it before
the sync. A wall in Arrt mode never runs it, and needs no new `.env` key.

    sudo apt-get update && sudo apt-get install --no-install-recommends mpv

The unit's `SupplementaryGroups` gains `render`. Install the unit as the runbook
says.

**Rolling back to an older revision** after this one has written the settings
file (saving any setting, or setting or changing the page's password) needs the
file put back to layout 1 by hand. Delete the slideshow keys from
`$CACHE_DIR/.settings.json` and set `version` to 1, or the older Player refuses
the file and names the version (`deploy/README.md` § The slideshow).

## 2026-11-10: A settings page on the Player, and a first run with no server configured

<!-- prawduct: type=feature | scope=settings-ui | release=v0.7.0 -->

The Player serves one page of its own: a settings page on port 8771. It sets the
server, the client token and the Player's name, and wears Arrt's design. A Player
with no server configured now starts that page, rather than refusing to start.

### What changed
- **Setup mode.** With `SERVER_URL` or `CLIENT_TOKEN` set neither in the
  environment nor on the page, the Player serves only the page and prints
  `go to http://<address>:<port>/setup?code=<code> to configure`. A missing
  `CACHE_DIR` still exits 2.
- **The page.** The first password is set with a one-time code printed at
  start, and has at least 8 characters. Sessions are an HMAC-signed cookie,
  form posts must come from the page's own origin, and wrong passwords are
  throttled. The token can be written and never read back. The server's
  address and its token move together. A key `.env` sets is read-only on the
  page. Saving restarts the Player onto what was saved.
- **The name** a Player goes by is its server's, once there is one, and
  `PLAYER_NAME` otherwise. `TV_CLIENT_NAME` is untouched.
- **Its look** is Arrt's, copied with its source recorded: tokens, typefaces
  and component rules. A test holds the copy to WCAG AA in both colour schemes.
- **The plane-isolation guard** lets the page's one module import
  `aiohttp.web`, and nothing else from aiohttp.
- Settings are kept in `$CACHE_DIR/.settings.json` (versioned, 0600). New
  `.env` keys: `UI_BIND`, `UI_PORT`, `PLAYER_NAME`.

### Confirmed by the owner (2026-11-10)
- Setup mode and the printed line.
- A password set on first run, with an 8-character minimum.
- The setup code printed and logged.
- The narrowed guard.
- Never re-pairing the television over a name.
- Arrt's look.
- How the page looks in a real browser.

**Consumer note:**

**Check `.env` before deploying.** At start the Player now refuses, with exit 2
naming the key:
- a `SERVER_URL` that is not an http(s) address with a host, or that carries
  a user name, password, query or fragment;
- a `CLIENT_TOKEN` containing whitespace;
- a `PLAYER_NAME` over 64 characters.

Port 8771 is now listened on, on every interface unless `UI_BIND` narrows it.
On the first start, the journal's `go to http…` line is how to set the page's
password (`deploy/README.md` § The settings page).

## 2026-11-10: The suite runs on the testament pool

<!-- prawduct: type=chore | scope=testament | release=v0.7.0 -->

The Player's suite runs on the testament pool, as Arrt's suites already do. The
move out of Arrt's repository did not bring that setup along.

### What was added
- `.testament.toml`: one container suite, the declared one
  (`uv run --frozen --group raster pytest` over `tests/`). `--group raster` is in
  the setup step too, because a plain `uv sync` uninstalls it and
  `tests/raster` then skips itself while the run stays green.
- `.devcontainer/Dockerfile`, the test image. It is Debian trixie, because the
  locked PyGObject builds from source against girepository-2.0, which bookworm
  lacks. It installs Python 3.13 through uv, the cairo, pango and girepository
  headers and a C toolchain for the build, DejaVu fonts (Pango with no fonts
  renders blank), git and tar, and ends as a non-root user. Both base images are
  pinned by digest.
- `AGENTS.md` § Running tests (testament's agent block), and CLAUDE.md's Test
  command points at it.

### Verified
- In the image, built locally: `uv sync --frozen --group raster`, then the whole
  suite passed with none skipped, the same count as a local run of the same tree.
- On the pool: `testament onboard -- tests/test_config.py` ran on a runner, and
  `testament run` ran the whole suite, all passed, with no fallback and nothing
  missing.

### Also carried: the settings page's records, after its deploy
The runbook, the settings-ui plan and `deploy/README.md` § The settings page
said the on-Pi checks had not been run. They ran when the wall Pi moved to
9ca66b2 on 2026-11-10, and all three records now say so. They ride this branch
because `develop` takes changes only by PR.

### Confirmed by the owner
The container executor and one suite, 2026-11-10.

## 2026-11-08: Pillow 13 and certifi, for their security fixes

<!-- prawduct: type=fix | scope=pillow-13 | release=v0.7.0 -->

The Player locked Pillow 12.3.0, the version Dependabot flagged on Arrt with 5
critical and 23 high alerts, among them JPEG and TIFF decoder buffer overflows and
decompression-bomb bypasses. The Player decodes every picture its server hands it
(`compose.py`, `kms.py`, `panel/epaper.py`), so it carries the same exposure. Pillow
goes to 13.0.0, with `pillow>=13.0.0` declared and a comment saying it is a security
floor; certifi to 2026.10.23 (one critical alert on Arrt); black to 26.10.1, matching
Arrt and the contract package. Pillow 13's incompatible changes were read against every
call site: the Player uses none. The whole suite, the raster group included, passes
under 13.0.0, and `tools/label_preview.py` starts. Arrt took the same upgrade in its
#411.

**Consumer note:**

No visible change. The image library the Player uses to read pictures is patched
against the vulnerabilities GitHub reported.
